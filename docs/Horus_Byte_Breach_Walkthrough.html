How it happened

Six stages, from login to full compromise.

Follow the line — every step below builds directly on the one before it.

01
Recon

Session setup & baseline recon

Logging in with a provided low-privilege doctor account and mapping every page, form, and API call via proxy before any testing began.

Burp Suite HTTP history  →  9 endpoints mapped
02
Exploit  ·  SQL Injection — Critical (CVSS 9.1)

Breaking the query with a single quote

The national-ID search field concatenated user input directly into a raw SQL query. A boolean payload bypassed the intended single-record filter entirely.

' OR '1'='1  →  all 78 insurance case records returned
03
Exploit  ·  Stored XSS — High (CVSS 8.2)

Planting a script that runs for anyone else

The medical-notes field rendered raw HTML via innerHTML, so any doctor account could store JavaScript that executes in every future viewer's browser.

<script>alert(document.cookie)</script>  →  stored, executes on load
04
Exploit  ·  Broken Access Control (IDOR) — High (CVSS 7.5)

A file endpoint that never asked "whose patient?"

The endpoint verified only that a session existed — never that the requesting doctor was actually assigned to that patient. Incrementing the ID was enough.

GET /api/patient/60  →  full file, different governorate, no check
05
Compound  ·  Auth & Session Weaknesses — Medium

No brakes on login, no seatbelt on the cookie

The login endpoint accepted unlimited password attempts with no throttling, while the session cookie shipped without the SameSite attribute.

0 rate-limit headers  ·  SameSite absent on connect.sid
06
Verify  ·  Remediation

Proving the fixes actually hold

Every exploit above was re-run against the patched application, using the exact same reproduction steps — each one now fails safely.

SQLi → empty result  ·  IDOR → 403 Forbidden  ·  XSS → literal text
What went wrong, in detail

Six issues. One critical chain.

Each one is common and well understood — which is exactly what makes the combination so effective.

CriticalCVSS 3.1: 9.1

SQL Injection (UNION-Based Data Exfiltration)

The national-ID search endpoint concatenates user input directly into a raw SQL query with no parameterization.

ImpactFull users table extracted, including bcrypt password hashes for every account.
FixReplace all string-concatenated SQL with parameterized queries.
HighCVSS 3.1: 8.2

Stored Cross-Site Scripting (XSS)

The medical-notes field accepts arbitrary text and renders it via innerHTML with no sanitization.

ImpactPersistent JavaScript execution and session-cookie theft for any user who opens the file.
FixRender user text with textContent, or sanitize with an allow-list library.
HighCVSS 3.1: 7.5

Broken Access Control (IDOR)

The patient-file endpoint returns any file to any authenticated user, without checking doctor-patient assignment.

ImpactAny doctor can enumerate and read every patient's medical file in the system.
FixAdd a server-side check comparing the session user against the file's assigned doctor.
MediumCVSS 3.1: 5.3

Missing Rate Limiting on Login

The login endpoint accepts unlimited authentication attempts with no delay, lockout, or CAPTCHA.

ImpactUnthrottled brute-force against any known national ID, including admin accounts.
FixApply per-IP / per-account rate limiting (e.g. 5 attempts per 15 minutes).
MediumCVSS 3.1: 4.3

Missing SameSite Cookie Attribute

The session cookie is issued with HttpOnly but without SameSite, weakening built-in CSRF resistance.

ImpactA malicious site could trigger a forged request with the victim's session cookie attached.
FixSet SameSite=Lax (or Strict) and the Secure flag on the session cookie.
LowCVSS 3.1: 2.4

X-Powered-By Information Disclosure

Every response includes the default Express.js header, disclosing the backend framework to any observer.

ImpactNarrows the search space for an attacker looking for framework-specific vulnerabilities.
FixDisable the header globally with app.disable('x-powered-by').

None of these six issues would make headlines on their own. A missing parameterized query. Unescaped HTML. A missing ownership check. An unthrottled login form. Individually, ordinary mistakes.

Chained together, they let any authenticated user read the entire patient database, hijack another user's session, and brute-force any account — without writing a single custom exploit.

That's the value of a structured methodology: several of these findings — missing rate limiting, missing SameSite — were only discovered because the full OWASP WSTG process was followed end-to-end, rather than testing for a pre-known list of vulnerabilities.

Closing the gaps

Six changes. Six findings solved.

All items below were implemented in the codebase and independently re-verified.

Parameterize every SQL query

Replace string-concatenated SQL so user input is always treated as data, never executable code.

Fixes #1

Render user text safely

Use textContent instead of innerHTML, or sanitize with an allow-list HTML library.

Fixes #2

Add object-level authorization checks

Verify the session user actually owns or is assigned to the requested resource, server-side.

Fixes #3

Rate-limit authentication

Apply per-IP / per-account throttling on the login endpoint, with logging on repeated failures.

Fixes #4

Harden the session cookie

Set SameSite and Secure attributes so cookies aren't attached to cross-site requests or sent in the clear.

Fixes #5

Disable framework fingerprinting

Turn off headers like X-Powered-By that disclose the backend stack for no functional reason.

Fixes #6
